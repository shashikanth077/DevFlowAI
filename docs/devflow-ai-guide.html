DevFlow AI, end to end

DevFlow AI turns a plain-language software requirement into a reviewed GitHub pull request. Nine specialised AI agents act as a software team: a business analyst, an architect, developers, QA, a security reviewer and a release engineer. A LangGraph StateGraph coordinates them, and a human approves every step with side effects.

Three principles

Agents propose, humans approve

Generated code runs in the sandbox only after an execution approval, and nothing is pushed until a release approval.

Verify, don't trust

LLM output is schema-validated, file edits are guarded, tests really run, and the review is independent and fingerprinted.

Never silent

Every agent execution, log line, diff, test run, review and MCP tool call is persisted, traced in LangSmith and streamed live to the dashboard.

End-to-end journey

What a user does and what happens behind the scenes. Steps in orange are human decisions.

  1. Sign in to the dashboard. The account uses JWT auth, and passwords are PBKDF2-hashed.
  2. Connect GitHub in Settings with a fine-grained token. It is validated against GitHub and Fernet-encrypted at rest.
  3. Create project: pick a repository and a base branch. Branches are listed with their protection status.
  4. Enter a requirement and click Start workflow. POST /api/workflows/start returns 202 and the graph starts on a worker thread.
  5. Requirement Analyst produces objectives, requirements, ambiguities and acceptance criteria.
  6. Repository Analyst clones the repo into an isolated workspace and detects languages, frameworks, test commands and relevant files.
  7. Architect designs the approach, the endpoints, the data models and a file plan.
  8. Task Orchestrator validates the task DAG and assigns tasks to the frontend and/or backend developer.
  9. Developers write complete files through the guarded workspace. They run in parallel, or in order when there are dependencies.
  10. Approve execution: review the exact sandbox image and commands.
  11. QA runs tests, lint and build in Docker. Failures go back to the responsible developer, within the retry limit.
  12. Code Review & Security combines automated checks with an LLM review. A rejection sends feedback back to the developers.
  13. Approve release: check the branch, files, tests and review verdict.
  14. GitHub Release creates the feature branch, commits only the approved files, pushes, and opens the PR. You get the PR URL, the commit SHA and a summary.

Human approvals & checkpoint recovery

How an approval gate works

  1. The node calls interrupt(payload). LangGraph saves a checkpoint and stops.
  2. The runner sees the interrupt and stores pending_approval, and the status becomes awaiting_approval.
  3. The dashboard shows the payload: exact commands for the execution gate, or branch, files, tests and review for the release gate.
  4. POST /approve {approved, comment} resumes the graph with Command(resume=…).
  5. Approve: the node returns and routing continues. Reject: workflow_status = cancelled and the graph goes to END, so nothing is pushed.
decision = interrupt({"gate": "release", "feature_branch": ..., "test_status": ...})
if not decision.get("approved"):
    return {"workflow_status": "cancelled"}

Checkpointing

The graph is compiled with a PostgresSaver (or SQLite or memory), using thread_id = workflow_id. A checkpoint is written after every super-step.

  • Interruption by approval: the run can wait for hours; resuming loads the checkpoint.
  • Crash or restart: on startup, resume_interrupted() finds workflows that are still running and calls graph.invoke(None), which continues from the last completed node.
  • Verified: test_checkpoint_recovery_after_crash kills a run inside QA, starts a new manager, and asserts that earlier stages were not re-run.
Nodes are written to be safe to re-run from their start. After an interrupt the gate node runs again, so all side effects happen after the interrupt() call.

LangSmith tracing

Every workflow becomes a trace you can open in LangSmith: graph nodes, each LLM call with model and token usage, and every MCP tool call, nested the way they actually ran. Select a run to see what it captures.

One root run per segment

A workflow pauses at each approval gate, so it has a start segment plus one -resume segment per decision. All share thread_id = workflow id, which LangSmith groups into a thread. The ids are stored on the workflow.

Feedback signals

human_approval_execution, human_approval_release, tests_passed, review_approved, workflow_completed, retries_used: attached to the trace so you can filter and chart quality.

Never fatal

If LangSmith is unreachable or a hook fails, the error is logged and the workflow carries on. Tracing is observability, not a dependency.

MCP: tools for agents, and DevFlow as a tool

  
The Model Context Protocol is used in both directions. Agents call tools on MCP servers, and external MCP clients (Claude Code, Claude Desktop) call DevFlow.

  

    
1 · Agents use MCP tools DevFlow = client

      
The architect, developers, reviewer and requirement analyst may run a short tool loop before answering. Tools come from the built-in devflow-repo server and any servers in the operator's MCP_SERVERS_FILE.

      
  • devflow-repo: list_directory, read_file, search_code, git_log, git_status, git_diff (all read-only)
  • stdio and streamable-HTTP transports
  • users opt in under Settings and can switch servers off

    
2 · DevFlow is an MCP server DevFlow = server

      
Run python -m app.mcp_tools.devflow_server with a DevFlow access token to let an MCP client drive workflows.

      4. 
    
    4. docker commit snapshots the container to a temporary image.
      5. 
    
    5. docker run --rm --network none runs each test, lint and build command with a hard timeout (killed on expiry).
      6.

    Testing & quality
    
  
    
    
    Backend (pytest, 96 tests)
    
      
      
        
    • Unit: security helpers, LLM service (validation retries, redaction, Anthropic and OpenAI wire formats), repository inspection and path guards, every agent, routing and reducers.
      • 
        
    • API: auth, settings (the API key is never echoed back), GitHub connect, repos and branches (mocked), validation and ownership.
      • 
        
    • End-to-end graph through the REST API: a test failure followed by a fix and a PR, max retries, review rejection, release rejection, cancellation, crash recovery from a checkpoint, and pytest really running in the Docker sandbox.
      • 
        
    • MCP: the repo server and a purpose-built policy server over real stdio and streamable-HTTP transports: read-only gating, scoping, redaction, truncation, budgets, timeouts, dead servers, prompt-injection fencing, and the DevFlow MCP server (which has no approve tool).
      • 
        
    • LangSmith: a recording fake of the LangSmith HTTP API verifies trace nesting (tool and LLM runs under their graph node), token usage, feedback, hide-content mode, and that no credential is ever sent.
      • 
        
    • The same suite passes on SQLite and on PostgreSQL (TEST_POSTGRES_URL).
      • 
      
    
    
    Frontend (Vitest + RTL, 23 tests)
    
      
      
        
    • Diff parsing and rendering, status chips, agent progress derivation.
      • 
        
    • Approval panel decisions, agent monitor, log merging for SSE plus polling.
      • 
        
    • Login flow and Create Project (connect repo → create project → start workflow).
      • 
        
    • MCP tool-call table, trace links, and the Settings integrations card.
      • 
        
    • tsc strict type-check and production build.
